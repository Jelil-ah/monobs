- [event] 2026-07-25 — init. Slug imposé `monobs-v1`. Entrée = brief de session Jelil, état vérifié sur disque à HEAD `0a63c2d`, release v0.2.0 publiée.
- [direction] Déclencheur : Jelil demande « du coup l'app est finie ? » puis « y'a pas de bouton quitter aussi je crois ». v1 = la version qu'un non-développeur installe, utilise et retire sans terminal.
- [direction] Jelil est non-développeur, pilote par Discord, apprend par schémas/tableaux, refuse les pavés. La spec reste courte ; le détail part en companions.
- [note] Périmètre entrant vérifié : 4 états (vert / rougeInjoignable / rougeSeuil / stale), 4 surfaces (barre de menu, popover, widget, notification), seuils disque ≥90 % / RAM ≥90 % / charge-par-CPU ≥2.0. Acquis, hors périmètre v1.
- [note] Story E1 livrée aujourd'hui : thème D2 « Braise » dans popover + widget, formatage d'âge unifié `30s/5min/2h/3j`, anneau de focus neutre, `scripts/scope-guard.sh`. Acquis.
- [constraint] Invariant produit acquis : l'arrondi d'âge est SUPÉRIEUR — ne jamais annoncer une donnée plus fraîche qu'elle ne l'est. Exclut toute troncature et tout âge négatif affiché.
- [capability] CAP-1 quitter l'app depuis l'app. Constat vérifié : `grep -rn "Quitter|terminate|NSApp.terminate|Quit" Monobs/*.swift` → zéro résultat ; `Monobs/MonobsApp.swift:173` déclare `.menuBarExtraStyle(.window)`, donc le clic ouvre le popover et aucun menu contextuel n'existe. L'utilisateur doit tuer le process. Bug priorité haute.
- [capability] CAP-2 identité visuelle de l'app. Constat vérifié : `Monobs/Assets.xcassets/AppIcon.appiconset/` ne contient que `Contents.json`, zéro image → icône générique macOS.
- [decision] Direction d'icône validée par Jelil (« on poursuis ») : octogone cristal 3D prune translucide flottant sur fond quasi-noir, orbe d'état verte au cœur, glow façon Thaw. Assets prêts hors repo. Détail → companion `icon-assets.md`.
- [capability] CAP-3 glyphe de barre de menu propre à Monobs. Constat vérifié : `Monobs/MonobsApp.swift:170` utilise `Image(systemName:)`, un symbole SYSTÈME statique. 24 frames PNG + `glyph-anim-spec.md` existent hors repo, jamais intégrés.
- [decision] La règle « pas d'animation » est rouverte UNIQUEMENT pour le glyphe de barre de menu. Popover et widget restent calmes. Glow = ressource rare réservée aux incidents.
- [decision] Multi-formes de glyphe (skins type RunCat) explicitement REPORTÉ par Jelil → Non-goal.
- [question] Q1 — l'animation du glyphe vaut-elle son coût (moteur de frames + budget CPU/batterie) face à un glyphe statique 2 états ? Non tranché par le brief, arbitrage produit → ne pas deviner.
- [capability] CAP-4 installation guidée. Constat vérifié : le README ne mentionne ni install, ni zip, ni clic droit. Symptôme observé aujourd'hui sur le Mac de Jelil : app lancée depuis `/private/var/folders/.../AppTranslocation/...` (quarantaine, lancée depuis le zip), plus deux copies concurrentes (`/Applications` + Bureau).
- [capability] CAP-5 désinstallation propre et documentée. Corollaire du même constat : deux copies concurrentes, aucun geste de retrait documenté.
- [question] Q2 — la désinstallation doit-elle être outillée (script) ou seulement documentée ? Arbitrage produit, non tranché.
- [decision] Angle mort Reduce Transparency / Increase Contrast → DANS le périmètre v1 (CAP-6). Justification : `Monobs/PopoverContent.swift:56` applique `.ultraThinMaterial` + stops translucides inconditionnellement ; sous ces réglages la surface principale se dégrade, ce qui casse la lisibilité de l'état — la fonction même du produit. Une v1 « finie » ne peut pas être illisible sur un réglage système standard.
- [decision] Angle mort anneau de focus macOS 13 → NON-GOAL assumé. Justification : `.focusEffectDisabled()` n'existe qu'à partir de macOS 14 ; sur le plancher 13 l'anneau système reste dessiné sous l'anneau neutre et peut porter l'accent utilisateur. Contourner exige de quitter le focus SwiftUI natif — coût structurel disproportionné face à un défaut cosmétique sur un seul palier d'OS. Limitation documentée, déjà consignée dans la story E1.
- [capability] CAP-7 garde d'API sur le formatage d'âge. Constat vérifié : `AgeFormatting.tiered(Int)` est public sans garde négative, `tiered(-1)` rend `"-1s"`. Les deux chemins UI gardent en amont, mais l'API publique reste mal-employable et l'invariant de fraîcheur n'est pas défendu à sa frontière.
- [capability] CAP-8 preuve de rendu. Constat vérifié : seule cible de tests = `MonobsKitTests` (`MonobsKit/Package.swift:15`) ; aucun test d'app/UI, de `Theme`, de focus, de matériau ou de contraste. Les 191 tests verts ne prouvent rien sur le rendu.
- [question] Q3 — faut-il créer une cible de tests app/UI pour couvrir le thème, ou une checklist manuelle signée sur Mac suffit-elle en v1 ? Arbitrage coût/valeur, non tranché.
- [constraint] Plancher macOS 13 (`MonobsKit/Package.swift`). Exclut toute API 14+ sans repli explicite.
- [constraint] Zéro dépendance externe (pas de SPM tiers). Exclut toute lib d'animation, de rendu ou d'auto-update ; tout est SwiftUI/AppKit natif.
- [constraint] Read-only : Monobs observe, n'agit jamais sur les serveurs surveillés. Exclut tout contrôle distant. « Quitter » agit sur le process local, ce qui ne viole pas la règle.
- [constraint] Repo public + lint CI `scripts/t-priv` bloquant : zéro chemin de machine de dev, zéro identifiant d'infra réel dans le code ou la doc. A déjà fait échouer un build aujourd'hui (commit `0a63c2d`). Exclut de committer captures, chemins absolus ou métadonnées d'assets non nettoyées.
- [constraint] Pas de compte développeur Apple payant → app non signée, non notarisée. Exclut l'installation par simple double-clic et tout auto-update signé ; impose de documenter le geste clic droit → Ouvrir et le piège App Translocation. La spec vit AVEC cette contrainte.
- [constraint] VPS de build Linux sans toolchain Swift → build et tests obligatoirement sur Mac distant. Exclut toute preuve de rendu produite en CI ; toute vérification visuelle exige une passe Mac.
- [decision] Non-goals retenus : skins multi-formes de glyphe, signature/notarisation Apple, actions sur serveurs, refonte du layout du popover, correction de l'anneau de focus macOS 13, auto-update in-app.
- [decision] Trois companions spawnés — contenu porteur en tableau ou en catalogue, hors forme du kernel : `icon-assets.md` (catalogue d'assets + livrables), `accessibility-notes.md` (angles morts et repli), `installation-notes.md` (gestes install/désinstall et pièges macOS).
- [assumption] A1 — les assets de `<design-workspace>/monobs/icon-d2/` sont finaux ; v1 les décline sans re-design.
- [assumption] A2 — l'icône du Dock/Finder reste nominale ; le changement d'état se lit sur la barre de menu, pas sur l'icône d'app.
- [assumption] A3 — le geste « quitter » doit être atteignable en ≤2 gestes depuis l'icône de barre de menu ; sa forme exacte (menu contextuel ou action dans le popover) reste au design.
- [assumption] A4 — v1 est publiée comme release GitHub avec `Monobs.zip`, même canal que v0.2.0.
- [assumption] A5 — aucune migration de réglages n'est requise entre v0.2.0 et v1.
- [question] Q4 — un Mac sous macOS 13 est-il disponible pour vérifier le plancher, ou v1 accepte-t-elle une vérification sur le seul Mac M4 récent ?
- [question] Q5 — sous Reduce Transparency, quel repli visuel : fond opaque prune sombre du thème Braise, ou fond système standard ?
- [question] Q6 — `appicon-incident.png` a-t-il un usage en v1, ou est-il réservé à plus tard (cf. A2) ?
- [question] Q7 — l'app n'étant pas signée, v1 publie-t-elle un checksum du zip pour vérifier l'intégrité du téléchargement ?
- [question] Q8 — le lancement au démarrage (login item) entre-t-il dans le périmètre v1, ou reste-t-il hors sujet ?

## Update 2026-07-25 — arbitrages tranchés + audit machine

- [direction] Jelil délègue explicitement tous les arbitrages (« t'as les skills pour tout trancher »). Les 8 questions ouvertes sont tranchées ici par le controller ; elles quittent `## Open Questions`.
- [decision] Q1 TRANCHÉE → glyphe STATIQUE deux formes (nominal, incident). Raison : mouvement permanent = coût CPU/batterie continu, et 24 PNG embarqués pour un élément de ~16 px. L'identité visuelle est acquise sans animation. SUPERSÈDE l'entrée « la règle pas d'animation est rouverte pour le glyphe » : l'animation devient un Non-goal v1 — report, pas abandon (recandidate en v2). CAP-3 se lit désormais sans clause conditionnelle.
- [decision] Q2 TRANCHÉE → désinstallation DOCUMENTÉE, aucun script livré. Raison : le geste a été exécuté à la main en moins d'une minute (arrêt du process + déplacement de deux copies) ; un script serait de l'abstraction prématurée. CAP-5 : la doc liste emplacements et gestes.
- [decision] Q3 TRANCHÉE → preuve de rendu par CHECKLIST MANUELLE SIGNÉE sur Mac, consignée dans le repo. Raison : une cible de tests UI macOS est un chantier en soi, hors périmètre v1. CAP-8 : une entrée datée par capacité visuelle (CAP-2, CAP-3, CAP-6) avec son résultat.
- [decision] Q4 TRANCHÉE → le plancher passe de macOS 13 à macOS 14. Raison décisive : AUCUN Mac sous macOS 13 n'est disponible pour vérifier ce palier (audit : les deux Macs joignables sont en 26.5.x). Un plancher non vérifiable est une promesse creuse. SUPERSÈDE la contrainte « Plancher macOS 13 ».
- [decision] Corollaire de Q4 : `.focusEffectDisabled()` devient disponible inconditionnellement, donc l'anneau de focus est purement neutre partout. SUPERSÈDE l'entrée « angle mort anneau de focus macOS 13 → NON-GOAL assumé » : le non-goal est RETIRÉ (caduc), l'angle mort est résolu par le plancher au lieu d'être assumé. Angles morts de rendu restants : 3 sur 4.
- [decision] Portage de Q4 à faire dans le code : `MonobsKit/Package.swift:10` (`platforms: [.macOS(.v13)]`) et les 4 blocs `MACOSX_DEPLOYMENT_TARGET = 13.0;` de `Monobs.xcodeproj/project.pbxproj` (Debug/Release des 3 cibles). Vérifié sur disque à HEAD `0a63c2d`.
- [decision] Q5 TRANCHÉE → sous Réduire la transparence, repli = fond OPAQUE prune sombre du thème Braise (pas le fond système). Raison : l'identité visuelle survit au réglage d'accessibilité ; on dégrade la translucidité, pas la marque.
- [decision] Q6 TRANCHÉE → `appicon-incident.png` reste HORS v1 ; asset conservé pour plus tard. Raison : cohérent avec A2 (l'icône du Dock reste nominale, l'état se lit sur la barre de menu). A2 est confirmée, pas contredite.
- [decision] Q7 TRANCHÉE → OUI, publier un checksum SHA-256 du zip dans les notes de release. Raison : l'app n'étant ni signée ni notarisée, le checksum est le seul moyen pour l'utilisateur de vérifier son téléchargement. Coût nul. Nuance portée en spec : la vérification reste OPTIONNELLE et hors du chemin nominal d'installation, car la comparer exige un terminal — ce que le Why exclut du parcours obligatoire.
- [decision] Q8 TRANCHÉE → lancement au démarrage (login item) HORS périmètre v1 → Non-goal. Raison : périmètre déjà large ; l'utilisateur n'en a jamais fait la demande.
- [note] F1 — audit de l'asset réellement publié en v0.2.0, en-tête Mach-O lu octet par octet : magic `0xcffaedfe`, THIN binary, `arm64` UNIQUEMENT. Ce n'est pas un binaire universel. Or le parc comporte un Mac Intel (`uname -m` → `x86_64`) décrit par Jelil comme sa machine de test : l'app publiée refusera de s'y lancer, ou dépendra d'une traduction indisponible. Défaut de distribution réel, pas théorique.
- [capability] CAP-9 distribution universelle (nouvelle, ID suivant non utilisé). Issue de F1. Ferme le défaut : la release doit embarquer les deux architectures.
- [constraint] Le binaire de la release doit être UNIVERSEL (`arm64` + `x86_64`). Exclut tout build mono-architecture limité à celle de la machine de build — ce qui a produit le thin `arm64` de v0.2.0.
- [assumption] A6 — le parc cible compte trois Macs : deux Apple Silicon (dont un, la machine principale, hors ligne donc non auditable à ce jour) et un Intel de test. v1 doit être installable sur les trois sans traitement particulier — exactement ce que CAP-9 garantit. Hypothèse et non fait établi : une seule des trois machines a été auditée directement. Aucun nom de machine, adresse ni nom d'utilisateur consigné (repo public, lint `scripts/t-priv` bloquant).
- [decision] La contrainte « le glow est une ressource rare » est reformulée : avec l'animation hors v1, aucune surface n'est animée en v1 ; le glow subsiste comme traitement visuel STATIQUE réservé à l'état incident. Raison : la clause « le mouvement n'est admis que sur le glyphe » devient fausse après Q1.
